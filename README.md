[中文](README_cn.md) | **English**

Hybrid on-device deployment of `gemma-4-E2B-it` for the MTK 8400 platform
(`ro.soc.model=MT6899`, Dimensity 8400, Android 16, adb root):

| Stage | Where | Recipe |
|---|---|---|
| Gemma 4 vision tower (16 layers, 768 hidden) | MDLA NPU, **two DLAs** | NeuroPilot mixed precision **W8A16** (int8 weights, 16-bit activations, FP boundaries), bf16 compute |

| Agent: inference, memory, planning, tools, history | CPU, same process as the runner | `runtime/agent/` |

## Why the split looks like this

* The vision tower is a fixed-shape, weight-heavy convolutional/attention
  stack: exactly what MDLA with int8 weights wants, and it removes ~150 M
  parameters of work from the CPU.
* The text backbone generates tokens one at a time. Every NPU invocation costs
  a graph boundary, and the MiniCPM-V measurements on this SoC show decode
  collapsing from ~62 token/s (MNN CPU) to ~2.6 token/s (per-layer NPU
  graphs). Text therefore stays on MNN Q4.

## On-device agent (native)

The runner is also the agent: one arm64 process owns the model, the memory store,
the planner, the tools and the conversation history, and the app only renders
what that process emits.

```text
app  --write-->  agent/request.json
native           recall -> context -> plan -> (tool call -> observation)* -> answer
app  <--tail---  agent/events.jsonl   (steps, tool calls, memory writes, metrics)
```

| Task | Where it lives | Notes |
|---|---|---|
| Model inference | `runtime/gemma4_hybrid_runner.cpp` | NPU W8A16 vision + MNN Q4 text; text turns reuse the KV cache through MNN's prompt cache, so only the new suffix is prefilled |
| Memory | `runtime/agent/agent_memory.cpp` | Bounded on-disk store (facts, preferences, notes, episode summaries) with BM25 + CJK bigrams + recency/importance decay, near-duplicate merging, pruning, and **slot-based updates**: "记住我叫李雷" then "改成记住我叫杨雷" replaces that record instead of keeping both |
| Planning | `runtime/agent/agent_planner.cpp` | Plan state machine driven by `make_plan`/`update_plan`; the runtime also records implicit steps so the UI always shows what happened |
| Tools | `runtime/agent/agent_tools.cpp` | 12 native tools (calculator, now, unit_convert, text_stats, remember, recall, forget, search_history, image_info, device_info, make_plan, update_plan) plus alias resolution for the names a 2B model invents |
| History | `runtime/agent/agent_session.cpp` | Per-session append-only transcript, rolling summary, compaction, session list / rename / delete |
| Protocol | `runtime/agent/agent_prompt.cpp` | The checkpoint's own function-calling syntax, see below |

None of that logic is in Java: the app writes a request document and draws the
event stream.

### The model calls tools in its own native syntax

`gemma-4-E2B-it` is post-trained on the function-calling syntax its chat template
defines, and the deployed Q4 export produces it spontaneously:

```text
declaration  <|tool>declaration:calculator{description:<|"|>...<|"|>,parameters:{...}}<tool|>
model asks   <|tool_call>call:calculator{expression:<|"|>17*23<|"|>}<tool_call|>
tool answer  <|tool_response>response:calculator{ok:true,result:<|"|>17*23 = 391<|"|>}<tool_response|>
```

`helpers/tools/agent_live_probe.cpp` (real weights on x86) measured where that block may
go: a user turn that *starts* with `<|tool_response>` makes the model close its
turn immediately, and putting it inside the model turn just before MNN's
`<turn|>`\n`<|turn>model`\n makes it re-emit the closing token and stop.  Leading
the observation with a plain text line and appending the native block works *and*
keeps MNN's prompt-cache prefix valid, which is what the runtime does.

### Context budget

| Item | Default | Notes |
|---|---|---|
| KV cache (`max_all_tokens`) | 2048 | prompt + generated |
| System prompt + tool declarations | 677 tokens | measured with the real tokenizer |
| Prompt budget | 1700 | hard ceiling per generation |
| History budget | derived (603) | prompt budget - system prompt - one turn's allowance |
| Answer reserve | 320 | `max_answer_tokens` |

Text turns run on the prompt-cache delta path (~20-160 tokens prefilled per turn
instead of ~900).  Anything that changes the conversation - a new session, a
compaction, an image turn - re-creates the MNN engine first, because
`Llm::reset()` does not fully clear Gemma 4's mixed sliding-window KV cache
(trap T15).

### Honest limits of the shipped Q4 export

* Tool calling and the multi-turn loop work, but the model cannot copy a token
  sequence reliably: asked to repeat `5927452215` it answers `51937423`, and
  `ZQ7-4412` becomes `ZQ3-4412`, with no tool involved.  Tools should therefore
  return values the model can restate simply, and the app shows every observation
  in its own card so the user sees the exact result.
* Tool *names* drift (`get_time`, `current_time`, `calc`, single-letter typos);
  the registry resolves aliases and one-character slips before failing.
* A deterministic routing hint (arithmetic, time, image, "remember", "recall") is
  appended to the user message, never to the system prompt, which has to stay
  byte identical for the prompt cache.
* A cancelled turn stops being streamed immediately, but the running decode step
  finishes first: the arm64 MNN runtime this delivery links does not export
  `setTokenCallback()`, so a step is bounded by `max_tokens_per_step` instead.

### Deployed and measured on the phone (2026-09-21)

| Metric | Value |
|---|---|
| NPU vision accuracy (step 9, agent-enabled runner) | cosine 0.998, 117 tokens, 592 ms |
| Agent service startup | 3.32 s (LLM load 2.88 s) |
| First turn, fresh session (full prefill) | TTFT 15.4-17.3 s (~900-1000 prompt tokens) |
| Later text turn (KV reuse) | 82-153 token delta, TTFT ~1-3 s |
| Decode | 16.1-16.6 token/s |
| Tool execution | calculator ran the user's expression: `17*23 = 391` |
| Image turn (after the fix) | dog fixture + "describe this image in detail" → "I can see a dog in the image." |

The phone exposed four things the x86 probe could not, all fixed in native code:
the Q4 export writes malformed tool calls on-device (`call:calculator::calculator{…}`,
a dropped argument list, stray `<|"|>` tails), so names are parsed as identifiers,
aliases/typos resolve, and the routing hint now spells the exact call for
arithmetic and clock questions with a deterministic fallback when the model drops
the arguments; the model's own answer text is unreliable for numbers (the tool
card is authoritative); the thinking channel leaks as plain text and is now
stripped like the checkpoint template does; and an empty generation is retried
once instead of ending the turn with "I could not produce an answer".

### Intent routing

Each turn is classified first (native pattern matching in
`runtime/agent/agent_intent.cpp`, no model call) and the resulting policy drives
the rest: whether long term memory is consulted, whether a tool is expected, and
whether the answer must stay plain text.  A greeting does not touch the memory
store, an arithmetic or clock question gets the exact call seeded by the router,
a memory question is answered from the store without tools, and an image
description forbids tools (that is what stopped the `image_info{data:…}`
attempts).  The decision is emitted as an `intent` event and shown as a card in
the chat.  For image descriptions, an answer that refuses, bounces the question
back or is too short is replaced by the shipped single-shot prompt ("Describe
this image.") - measured on the phone: "This is a photograph of a dog outdoors.
The dog appears to be a light-colored … medium-sized dog with a relaxed
expression …".

### Attachments are one-shot

An attachment applies to the message it is sent with: after the turn is sent the
chip returns to 未附加图片, 清屏 also detaches it, and a 移除图片 button detaches
on demand.  Follow-up questions about the image still resolve through the session
transcript (the image turn keeps its cached canvas).

### Tool escalation and pinned advice

The same tool failing the same way twice tells the model to change strategy
instead of retrying the identical call (Mobile-Agent-E's `err_to_manager_thresh`),
and `agent-config.json` can pin deployment advice (`system_tips`, e.g. "Answer in
the user's language") into the system prompt, where it is rendered as the
`DEPLOYMENT NOTES (always apply)` block.

### Greetings and stray context

A greeting gets its own intent (`greeting`): no memory lookup, no tools, plain
text.  On the phone "Nihao" following an image turn used to be answered with
"I didn't understand what you want me to do with the image" - the image was still
in the session context and the small model latched onto it.  A greeting answer
that mentions an image is now rejected once and the model is asked for a plain
greeting; measured on the phone the turn ends with "Hello! How can I assist you
today?".  The earlier image stays in the transcript on purpose, so a follow-up
question about it resolves through the cached canvas.

### Image turns

An image turn now keeps the same path for every step: the runtime hands the
driver the image descriptions with each call, the driver prefills incrementally
only while its KV state is a prefix of the new prompt, and otherwise re-runs the
vision tower and the full prefill (the earlier bug was that step 2 of an image
turn - after a tool call or a retry - went down the incremental path and failed
with "an image turn must use a full prefill").  The image hint asks for a
plain-text description and deliberately does not mention `image_info`, because
the Q4 export otherwise tries to hand the image bytes to that tool; an
unparseable tool-shaped answer now triggers one plain-text retry.

Measured on the phone: the dog fixture + "please describe this image in detail"
answers "I can see a dog in the image."  Open-ended advice ("how to make this
image better") is still beyond this export - it produces a broken tool fragment
or two unrelated tokens - so the UI ships a "描述图片" quick action for the path
the deployment actually validates.

## Memory system

Three layers, each with its own lifetime: the session transcript (everything
said, deleted with the session), the rolling per-session summary, and the
cross-session store.  Only the last one is *memory* in the sense the UI means -
`runtime/agent/agent_memory.{h,cpp}`, a plain-file store so the data survives an
app update and can be read with `cat`:

```text
<agent_dir>/memory/memories.jsonl   one JSON record per line
<agent_dir>/memory/state.json       { sequence, updated_ms, records }
```

| Field | Meaning |
|---|---|
| `id`, `text`, `kind` | `m<N>`, the stored sentence, and `fact` / `preference` / `note` / `episode` |
| `importance`, `pinned` | the 0-1 weight used by search and pruning; pinned records are never pruned and always injected |
| `created_ms`, `updated_ms`, `last_access_ms`, `access_count` | the recency and frequency signals |
| `session`, `turn`, `tags` | provenance, so a record can be traced to the turn that wrote it |

**Writing.**  `AgentRuntime::write_memories()` runs after every turn.  The rule
extractor (`extract_memories()` in `agent_prompt.cpp`) turns an explicit
"记住…" / "remember …" into a `fact` (importance 0.9), an identity statement
("我叫…", "我住在…", "call me …") into a `fact` (0.8) and a preference
("我喜欢…", "i prefer …") into a `preference` (0.7); the imperative prefix is
stripped, so the store holds "我叫杨雷" and not "记住: 我叫杨雷".  A correction
marker ("改成", "改为", "instead") trims the text to the corrected tail and flags
the record, so it replaces the earlier value instead of adding a second one.
Anything else is recorded as an `episode` ("Q: … -> A: …", importance 0.3),
which the store discards unless `store_episodes` is enabled - turn episodes
belong to the session transcript and are found through `search_history`.  Each
write emits `memory_write` with the id, the kind and whether the record was
`new`, `merged` or `updated`.  `GEMMA4_AGENT_MODEL_MEMORY=1` adds a small extra
model pass that can replace the rule output (off by default: the rules are what
the shipped Q4 export was validated with).

**De-duplication.**  `MemoryStore::add()` tries three rules in order and stops at
the first match:

1. **slot conflict** - `extract_slot()` maps the leading pattern to a key
   (`name`, `city`, `job`, `preference`); a different value under the same kind
   and key replaces the old record, so "记住我叫李雷" followed by "改成记住我叫杨雷"
   leaves one record;
2. **explicit correction** - a record flagged `correction` replaces the most
   similar record of its kind once the token Jaccard similarity reaches 0.2, even
   when the wording changed a lot;
3. **near duplicate** - Jaccard >= 0.72 merges into the existing record (longest
   text wins, tags are unioned, importance is raised, the access count bumped).

**Retrieval.**  `MemoryStore::search()` is a local BM25 pass (k1 = 1.2, b = 0.6)
over the tokens from `tokenize()`: ASCII words lowercased, and for CJK every code
point plus every bigram, so "手机" also matches "我手机壳是紫色的".  The lexical
score is multiplied by a kind weight (episode 0.55, fact/preference 1.0, note
0.9), by `0.6 + 0.8 * importance` and by a recency factor
`0.7 + 0.3 * 0.5^(age / half_life)` (14-day half-life), gets
`1 + 0.05 * min(access_count, 8)` for frequently used records and a 1.5 bonus for
an exact phrase match, and `1 + 0.5 * importance` when pinned.  Anything below
`memory_min_score` (0.12) is dropped, so a greeting recalls nothing at all.

`AgentRuntime::recall()` wraps that: it returns nothing when `"memory": false`,
multiplies hits made in the *current* session by 1.6 (a fact this conversation
just established has to beat an older session's answer to the same question),
always appends pinned records and caps the list at `recall_top_k` (4) + 4.  The
result is prepended to the current user message - never inserted as its own
message, because a new message in the middle of the prompt invalidates the KV
prefix:

```text
[MEMORY] earlier sessions may have stored this about the user. Use it only when it answers the current message; ignore it otherwise:
- (preference m7) 我喜欢紫色
[END MEMORY]
```

The wording is deliberate: the phone once answered "它是什么颜色的？" (about a
picture) with the *remembered* favourite colour, because a recalled fact looked
like an answer.

**Lifecycle.**  Above `memory_max_records` (500) `prune()` ranks the store by
`2 * importance + recency + 0.1 * min(access_count, 8)` (episodes count 0.6) and
drops the tail; pinned records survive regardless.  `clear(kind, keep_pinned)`
and `remove(id)` back the UI's "清空全部记忆" and the per-record delete, and the
`remember` / `recall` / `forget` tools - with alias resolution for the names a 2B
model invents - address the same store from inside a turn.  A record's text is
clamped to 3 * `max_memory_chars` bytes on the way in.

## Session history and context management

`runtime/agent/agent_session.{h,cpp}` owns the transcripts; `render_history()`,
`compact_history()` and `update_session_notes()` in `agent_runtime.cpp` own the
policy that decides what the model actually sees.

```text
<agent_dir>/sessions/index.json         sequence + one meta per session, newest first
<agent_dir>/sessions/<id>/meta.json     title, timestamps, turns, compactions, summary, notes
<agent_dir>/sessions/<id>/turns.jsonl   append-only, one JSON object per completed turn
<agent_dir>/sessions/<id>/images/       the cached canvases of the image turns
```

A turn record stores *the exact `messages` the model saw* - user, tool calls,
observations, answer - not just the visible question and reply.  Replaying that
verbatim makes the prompt a strict prefix extension of the previous turn, which
is what lets MNN's prompt cache prefill only the new suffix; the transcript is
therefore append-only (`append_turn`), and it is rewritten only when an image
turn has to be replaced by its text note.  Each record also carries the timing
and usage of its turn (`ttft_ms`, `prefill_ms`, `npu_ms`, `decode_tps`,
`prompt_tokens`), which is where the numbers the app displays come from.

**What goes into the prompt.**  `render_history()` assembles the system prompt,
the rolling summary (if one exists), every turn after `summary_upto`, and then
this turn's own exchanges.  An image contributes its NPU soft tokens *only in the
turn that carried it*: an older image turn renders as `<|image>…<image|>` replaced
by `[image: <note>]`, where the note is what the model said about the picture plus
`; described as: …`, and that substitution is persisted.  So a later prompt
carries a text description instead of 130 soft tokens and never re-runs the
vision tower (`reuse_history_images` pins the soft tokens back on purpose).
Tool calls and observations inside a retained turn stay verbatim; they are folded
only by compaction.

**Compaction.**  When the transcript no longer fits the history budget - or the
assembled prompt is over `context_budget_tokens` - `compact_history()` asks the
model for a summary of the oldest turns (one auxiliary pass, <= 220 tokens, fed
the existing summary as `EXISTING SUMMARY`), stores the result in the session
meta as `summary` + `summary_upto`, bumps `compactions`, emits
`context_compacted` and forces a full prefill on the next step.  The newest
`recent_turns_min` (2) turns are never summarised, and a compaction never folds
fewer than `compaction_min_turns` (4) turns at once: an earlier build folded one
turn per message and produced 17 compactions in 28 turns, each costing a summary
generation plus an engine re-creation.

**Budget.**  `history_budget_tokens()` derives the transcript budget from the
prompt budget: `context_budget_tokens` (1700) minus the measured system prompt
with its tool declarations (677) minus a 420-token allowance for the turn itself,
floor 128 - 603 tokens, the number in the table above and in helpers/STATUS.md.
Setting `history_budget_tokens` in `agent-config.json` pins an explicit value
instead.  `"history": false` switches to fresh-context chat: system prompt,
current message and this turn's exchanges only.

**Session notes (Notetaker).**  `update_session_notes()` appends one bounded
bullet for every turn that left something behind - `[image t7] <what the image
showed>`, `[memory t7] <what was stored>`, `[tools t7] calculator, now -> <answer
head>` - keeping the last `session_notes_lines` (8) lines and
`session_notes_chars` (900) characters in the session meta, so the digest survives
a restart.  It is injected into the *current* user message
(`[SESSION NOTES] earlier in this conversation: …`) instead of in front of the
history, and is suppressed on turns the runtime can already answer by itself
(arithmetic, clock, unit conversion, text stats): the evaluation A/B caught an
arithmetic turn that answered nothing with the notes in the prompt and
`42+16 = 58` with them removed.  It is also what keeps an older image usable
after its soft tokens leave the window.

**Sessions and controls.**  `create()` / `open()` / `rename()` / `remove()` work
through `index.json`, which is rebuilt by scanning the session directories when it
is missing, so a damaged index never hides the history.  A new session's title is
the first user text (capped at `session_title_chars`), and at most `max_sessions`
(40) sessions are kept - the oldest are deleted with their directory.  The app
drives it all through `request.json` (`new_session`, `open_session`,
`delete_session`, `rename_session`, `list_sessions`, `history`, `compact`,
`reset`) and mirrors the event stream (`turn_start`, `context`,
`context_compacted`, `session_notes`, `answer`, `turn_end`); "删除全部会话" in the
session tab is one tap and one confirmation.

The two-tier windows borrowed from the Mobile-Agent family are the reason for the
shape above, but the shipped runtime implements them as "an image lives in its own
turn" plus compaction: `image_window_turns`, `tool_detail_window_turns`,
`recent_turns_max` and `max_context_turns` are still parsed and reported by
`capabilities`, but only `recent_turns_min`, `compaction_min_turns` and the notes
limits drive the policy.

## Vision graph

`helpers/src/gemma4_vision.py` rebuilds `Gemma4VisionModel` from the checkpoint as two
static ONNX shards:

```
front : canvas  float32 [1, 4, 720, 864]   (RGBA letterbox, alpha = padding)
             -> patch states float32 [1, 1, 2430, 768]
tail  : pooled  float32 [1, 1, 270, 768]   (3x3 average on the CPU, pre-scaled)
             -> soft tokens  float32 [1, 1, 270, 1536]
```

Everything geometric is baked in as a constant: the learned patch position
embedding, the 2D (x/y) rotary embedding and the 3x3 spatial pooling matrix.
The first operator is a stride-16 convolution that selects the 768 pixel
channels of every patch and, in its last output channel, reads the coverage of
the alpha plane; the additive attention mask is that coverage scaled by
`-30000`.  Keeping the mask inside the convolution is deliberate: a strided
slice on the input tensor is scheduled on MVPU, whose compiler needs an OpenCL
host, and handing a second tensor across the `EDPA → MDLA` boundary makes
NeuroPilot insert a bridge (both fail `--disallow-bridge`).

Two more constraints come from the hardware, not from the model:

* **bf16 compute** (`--cast-fp32=bf16`): vision activations reach ~2100 and
  squaring them for the RMSNorm overflows fp16.
* **Sharding**: a graph that contains the pooling MatMul compiles but makes
  MDLA return an all-zero output, so the average runs on the CPU and the tail
  DLA holds only RMSNorm + projection.

The runner letterboxes the aspect-preserving resize into the top-left of the
864x720 canvas, fills the alpha plane for the padding patches and drops the
pooled bins that only cover padding, which reproduces the HuggingFace pipeline
exactly:

```text
torch vs HuggingFace : cosine 1.000000 (MAE 1e-6) across dog/cat/document/qrcode
ONNX  vs torch       : cosine 0.9999999
```

`helpers/src/sanitize_onnx.py` constant-folds the shape plumbing that
`torch.onnx.export` emits for `chunk()`/`view()`; MDLA cannot execute `Shape`,
`Gather` or dynamic `Reshape`, and NeuroPilot is invoked with
`--disallow-bridge`, so a successful build contains no CPU/OpenCL fallback.

### Canvas profiles (geometry is a build-time choice)

Because every geometry-dependent tensor is baked in, a different canvas means a
different DLA pair, runner and APK:

| profile | patch grid | canvas | max soft tokens | front DLA |
|---|---|---|---:|---:|
| default | 54x45 | 864x720 | 270 | ~2.2 s |
| **shipped** | **30x39** | **480x624** | **130** | **0.57 s** |
| alternative | 36x36 | 576x576 | 144 | 0.51 s |

```bash
./helpers/scripts/11_switch_canvas.sh 30 39     # rebuild everything into out-30x39/
./helpers/scripts/09_deploy_device.sh           # NPU accuracy check (cosine vs HuggingFace)
./helpers/scripts/10_run_demo.sh                # install the matching APK
```

`env.sh` derives `GEMMA4_CANVAS_W/H`, the soft-token budget and the output
directory (`out-<W>x<H>/`) from `GEMMA4_GRID_W/GEMMA4_GRID_H`; the text backbone
in `out/mnn/` is shared because it does not depend on the canvas.  The APK gets
the same numbers through `-PgridColumns/-PgridRows`, and its header prints them
(`480x624 fit + padding, W8A16 vision`), so a mismatch between the compiled DLA
and the letterbox the app writes is visible at a glance - the runner rejects a
canvas whose header disagrees with its own geometry.

The smaller canvas is not free: landscape inputs (documents, QR codes) lose the
most tokens and the model can stop "seeing" them.  Measurements and the PC side
of that comparison are in [helpers/STATUS.md](helpers/STATUS.md).

`helpers/scripts/12_reproduce_all.sh` defaults to the shipped 30x39 profile (`out-30x39/`),
checks every prerequisite before it starts, runs steps 1-12 (the host agent test
suite, the arm64 runner, the APK and the x86 live agent probe) plus the manual
regeneration, and finishes with consistency checks (DLA/TFLite/MNN/APK present,
assembled weights byte-identical to the export - trap T16).  Use `--grid 54 45`
for the original profile, `--from N` to resume, `--no-device` to stop after the
APK, `--force` to ignore existing artefacts.  It refuses to start when `$OUT`
already holds a graph for another canvas, because step 01 would silently reuse
it.  Everything is teed into `logs/reproduce-<timestamp>.log`.

A rebuilt APK can hit AGP's `integer overflow` in `:app:packageDebug`: the
incremental packager works in 32-bit sizes and the APK is 2.9 GB.  Step 8 detects
that message and retries after `:app:clean` (non-incremental packaging), so a
rerun needs no manual cleanup.

`helpers/scripts/00_clean_generated.sh` deletes only what the pipeline generates (`out*/`,
`logs/`, `work/`, the Gradle build dirs, `__pycache__`); the documentation, the
tools and every input are untouched.  It prints the plan with sizes and asks
before deleting unless `--yes` is given; `--device` also cleans the phone.

## Runtime contract

The agent service is a resident process shared by the chat UI and the legacy
single-shot demo path:

```text
gemma4-d8400-runner --agent-service CONFIG VISION_DLA RUNTIME_ROOT AGENT_DIR [MAX_TOKENS]
gemma4-d8400-runner npu CONFIG VISION_DLA CANVAS_BIN REFERENCE_BIN
gemma4-d8400-runner --service CONFIG VISION_DLA CANVAS PROMPT REQUEST STOP LOG READY
```

| File (under `RUNTIME_ROOT/agent/`) | Direction | Contents |
|---|---|---|
| `request.json` | app -> native | `{"type":"turn","text":"...","image":"app-input-fp32.bin"}` plus `new_session`, `open_session`, `delete_session`, `rename_session`, `list_sessions`, `history`, `list_memories`, `delete_memory`, `clear_memories`, `remember`, `compact`, `capabilities`, `reset`, `cancel` |
| `events.jsonl` | native -> app | append-only JSONL: `hello`, `turn_start`, `recall`, `image`, `context`, `plan`, `step_start`, `step_delta` (base64 UTF-8), `step_end`, `tool_call`, `tool_result`, `tool_alias`, `memory_write`, `context_compacted`, `answer`, `metrics`, `turn_end`, `error` |
| `response.json` | native -> app | reply to query requests (history, lists, capabilities) |
| `cancel` | app -> native | sentinel that stops streaming for the running turn |
| `service-ready` | native -> app | written once the DLAs and the LLM are loaded |

The legacy path stays byte compatible: the app writes `app-input-fp32.bin` (the
letterboxed canvas, RGB planes in [0, 1]), `app-prompt.txt` and `app-request`,
and the same process answers with the streaming token log plus `RESULT` metrics
the screen-on/off benchmark parses.

## Repository layout

The demo is `android/` plus `runtime/` (the arm64 process the app drives) and
`helpers/scripts/`, the steps that build, assemble, deploy and run it.
Everything that only prepares its inputs or measures it lives under `helpers/`.

| Path | Contents |
|---|---|
| `android/` | the Gradle demo app (Java, no native build step) |
| `runtime/` | `gemma4_hybrid_runner.cpp` and `runtime/agent/`, compiled by `helpers/scripts/06_build_runner.sh` |
| `3rd/` | vendored MNN fork, host `MNNConvert`, arm64 `libMNN.so`, NeuroPilot device libraries |
| `env.sh`, `agent-config.json` | the shared environment (`MTKG`, `OUT*`, `LOGS`, toolchain paths) and the agent runtime config |
| `helpers/scripts/` | `00_clean_generated.sh` and `06`-`12`: build the runner, assemble assets, build the APK, deploy, run the demo, switch canvas, one-shot reproduction |
| `helpers/STATUS.md`, `helpers/01`-`05`, `helpers/src`, `helpers/tools`, `helpers/tests`, `helpers/inputs`, `helpers/docs`, `helpers/profiles`, `helpers/minicpmv46` | the measurement and analysis report, checkpoint -> DLA/MNN conversion, host probes and evaluation harnesses, calibration images, manuals, and the leftover scripts of the MiniCPM-V reference demo |

See [helpers/README.md](helpers/README.md) for that half in detail.  Generated
artefacts stay at the root (`out/`, `out-<W>x<H>/`, `logs/`, `work/`) whatever
step produced them.
